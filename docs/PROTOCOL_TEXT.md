# 四工位TCP文本协议：工位号、组别号与检测结果

当前版本：v1.5.0-station-groups。按最新确定的字段顺序接收下列两种结果报文，不额外增加工号或检测编号。服务器不评分、不建场次、不下发标准。

## 1. 直接发送

电机螺钉，6段（包含项目和end）：

```text
screw,工位号,组别号,螺钉数量,检测结果,end
screw,1,G1,4,OK,end
screw,2,002,3,NG,end
```

包装箱，8段（包含项目和end）：

```text
packaging,工位号,组别号,完整条码,LOGO结果,火焰标识结果,总结果,end
packaging,1,G1,001234-AbC,OK,NG,NG,end
packaging,2,002,005678-DeF,NG,OK,NG,end
```

使用UTF-8、**英文逗号**（`,`，不是`，`）、小写项目名和`end`，不附加空字符、不要求换行。`end`前也有逗号；字段中不使用引号或反斜杠转义。

| 字段 | 规则 |
|---|---|
| 工位号 | `1`或`2`，与项目共同定位四个工位；不接受01、空格或其他值 |
| 组别号 | 1～64字符非空文本，不含首尾空白、英文逗号或控制字符；保留前导零和大小写，例如001、G1 |
| 螺钉数量 | 0～2147483647的ASCII十进制非负整数，最多10位；不接受符号、小数、科学计数或布尔值 |
| 完整条码 | 最多512字符，原样保留前导零、大小写、首尾空格和Unicode；不能含英文逗号、换行或控制字符 |
| 检测结果、LOGO、火焰、总结果 | 各自必填，仅大写OK或NG，顺序固定，不细分原因 |

没有读到条码时保留空字段：`packaging,1,G1,,OK,NG,NG,end`。不能以省略字段代替空字符串。

## 2. 结果的来源

电机的检测结果由参赛端上报，服务器不由数量重新判定。即使收到`4,NG`或`0,OK`，也如实记录原值。

包装箱的LOGO、火焰、总结果各自由参赛端上报。服务器另行计算条码校验：MATCH（完全匹配）、MISMATCH（不匹配）、UNCONFIGURED（未配置标准）、UNSELECTED（有清单但本工位未选标准）、UNREAD（上传空条码）。**条码不匹配不会把上报总结果OK改成NG，LOGO/火焰NG也不会覆盖总结果。** 页面明确标注“检测结果（上报）”和“总结果（上报）”，条码校验单列。

标准由管理员通过本地JSON清单导入，两个包装箱工位分别选择。组别号不决定标准，变更组别不需要重连。不做标签印刷型号文字OCR。换箱前先等上一件结果保存再切换标准；协议没有样件ID，首次迟到结果只能按入库当时的标准校验。

## 3. 分帧、连接和回执

默认TCP9000，网页9080。四个工位可并行，每个项目+工位一个活动连接；同一连接不能更换项目或工位，后来的连接不能抢占。新组别在同工位继续上传即可。

接收器按**固定字段位置**识别结尾，而非查找任意`end`子串。条码为`end`或`ABend001`均可：`packaging,1,G1,end,OK,NG,NG,end`。

拆包、UTF-8字节拆分、结束标记拆分、无换行粘包均由接收缓冲处理。同工位可连续发送：

```text
screw,1,G1,4,OK,endscrew,1,G2,3,NG,end
```

上例保存两条记录、回复两次`ACK,end`。也容忍帧间LF/CRLF。客户端同样须缓存解析回执，不能把一次recv当成一次报文。建议一次发一条，等ACK后再发下一条。

| 情况 | 回复 |
|---|---|
| 提交数据库成功 | `ACK,end` |
| 格式/字段不合法 | `ERR,FORMAT,end` |
| 工位被占用 | `ERR,STATION_BUSY,end` |
| 本连接切换项目/工位 | `ERR,STATION_MISMATCH,end` |
| 超长/频率超限 | `ERR,LIMIT,end` |

ACK仅确认保存，不含标准条码、校验结论、得分或自动重算结果。错误不会产生NG记录。错误分帧不猜测下一边界，会断开；字段错误累计5次断开。缺少end的数据不会显示，超过5秒不完整或16KiB上限后断开。每连接最多100帧/秒。

连接后可等待再发送第一条结果或可选的`hello,screw,1,end`／`hello,packaging,2,end`，回复`HELLO,end`；不再要求5秒内标识工位，标识后空闲每5秒发`ping,end`，回复`PONG,end`；30秒无有效消息断开。hello不产生检测记录，也不设置组别。断线保留历史、清除当前在线组别，重连后旧结果标为历史。

**每条完整有效文本都是一条新检测。** 相同内容连续到达也分别记录。没有检测编号，ACK丢失后无法自动区分重试和新检测；先核对服务器记录，不盲目重发。服务端内部UUID不要求上报，也不代表客户端去重协议。

## 4. 升级与兼容

当前文本比旧文本多一个结果字段，并将原工号字段明确改为组别号。旧5段screw/7段packaging报文、遗漏工位号、额外工号字段均不接受，不猜测位次；不完整布局可能等待直到超时，不能把没有ACK当成已保存。

旧JSON v2单独保留，仍按LF分帧、worker_id和msg_id语义处理，同一连接不能混用文本/JSON。旧JSON没有新组别/检测结果/总结果，页面对应字段显示`—`，不能把旧工号改名充当组别。

新库schema3先备份再添加可空字段。旧记录不填假组别或假结果，原工号和原始报文留存；CSV/JSONL追加新字段以便核对。标准JSON批量导入规则不变。升级前停止进程、备份目录，拉取后用`python web_server.py`重启，已有标准/凭据无需重建。

```powershell
python station_client.py --project screw --station 1 --group-id G1 --count 4 --result OK
python station_client.py --project packaging --station 2 --group-id G2 --barcode "001234-AbC" --logo OK --flame NG --result NG
```

`--result`显式必填；文本模式不接受--worker-id或--msg-id。原send_result()保留JSON行为，新send_text_result()要求规范化字典中的group_id和detection_result/total_result。CLI的--json-v2仅用于旧JSON兼容，使用--worker-id，不可混入新组别/结果参数。

TCP无身份认证或加密，只部署于可信隔离网络或VPN/SSH，不直接暴露公网。标准、原始日志与维护操作仍受Web登录、Origin、CSRF保护。
