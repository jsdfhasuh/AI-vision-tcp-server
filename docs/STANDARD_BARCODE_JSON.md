# 包装箱标准清单：批量 JSON 导入与分工位选择

版本：v1.4.1-catalog。一个 JSON 文件可录入多个包装箱的完整标准条码；两个包装箱工位分别选择当前使用的标准。**不是“上传条码出现在清单任意位置就通过”。** 不新增轮次、评分、印刷型号文字识别或目标下发。

## 文件格式

```json
{
  "boxes": [
    {"id": "BOX01", "name": "1号包装箱", "standard_barcode": "001234-AbC"},
    {"id": "BOX02", "name": "2号包装箱", "standard_barcode": "005678-DeF"},
    {"id": "BOX03", "name": "3号包装箱", "standard_barcode": "009012-GhI"}
  ]
}
```

仓库示例：`examples/packaging-standards.example.json`。管理页提供相同的固定示例下载，不会下载实际比赛答案。可将文件命名为 `packaging-standards.json`。

`id` 是服务器内部标准编号，1～64字符，仅字母、数字、下划线、短横线，首字符为字母或数字，区分大小写且不得重复。`name` 是页面显示名称，非空、最长100字符，不参与匹配，更不是需要OCR识别的型号文字。`standard_barcode` 必须是非空字符串，最长512字符；前导零、大小写、首尾空格和Unicode原样保留，完整字符串精确比较。不同编号可以使用相同条码，例如实际物料确实使用同一个型号条码。

一个文件最多1000条，且UTF-8文件不超过256 KiB；长条码时可能先达到文件大小限制。可带UTF-8 BOM，支持Windows CRLF。不接受数字型条码、重复JSON字段、重复编号、额外字段、注释、尾随逗号、控制字符或非法Unicode。任意一条不合规，整个导入拒绝，不会只录入前半部分。

工号、LOGO、火焰标识不放在此文件中，它们仍由工位通过TCP v2上传。标准编号和名称不要求选手上传。

## 管理页操作

1. 登录“包装箱检查”，选择本地JSON文件。这里的本地是打开浏览器的电脑，不是服务器目录。
2. 核对只读清单预览、数量；可以按编号、名称或条码查找。此时显示“待导入”，原配置没有变化。
3. 点击“导入并生效”，确认整批替换。首次批量导入后，两个工位都处于未选择标准状态，不自动取第一条。
4. 在1号工位的“当前标准包装箱”中选择对应条目，点击“应用标准”；2号工位独立操作。允许两工位选同一条，也允许分别选择不同条目。
5. 同一包装箱连续检测不用重复选择；换箱时更换对应工位的标准。不创建比赛场次或测试轮次。

例如1号工位选BOX01、2号工位选BOX02，两个工位都上传`001234-AbC`时，1号匹配、2号不匹配，即使该条码在清单中存在。工号只表示操作者，不用于选择标准。

**换箱前先等待上一件的结果入库，再切换标准。** 当前协议不包含样件编号或标准版本，服务器无法从迟到报文中知道它属于切换前的实物；按新检测首次入库当时的工位标准校验。ACK丢失而原报文已入库的重试仍返回原记录，不重判。

## 清单更新、保存与历史

导入是**整批替换，不是追加**。增加包装箱时，请在同一个文件中保留原条目再添加新条目。修改本地文件后需要重新选择并导入；不自动扫描或监听文件。

重导后，已选条目的编号仍在且条码未改变，则保留该工位选择（名称变更不影响选择）；条目被移除或同编号的条码改变，该工位的选择被取消，需再次明确选择。另一工位未受影响的选择保留。

`{"boxes":[]}` 明确清空清单并取消两个工位的选择，网页会确认。清单为空显示“未配置标准”；清单存在但该工位没有选定条目显示“未选择标准”。这两种状态都不是不匹配或NG。客户端上传空条码仍是“未读取条码”。LOGO和火焰的OK/NG独立保存。

配置、两工位选择和配置版本存入服务器的`station-results.sqlite3`，重启后保留。每次检测记录当时的标准编号、名称、完整条码和配置版本。修改清单、切换标准、清空清单都不改写历史。管理端可见“本条校验标准”，CSV/JSONL导出包含完整历史快照；公共展板和TCP回执不公开标准清单、所选标准或标准条码。

多人同时操作时按配置版本检查；清单导入与任一工位选择共用一个配置版本。过期操作返回409，不静默覆盖。轮询不会覆盖待导入文件或未应用选择。出现版本冲突，重新载入后再次核对；提交响应超时表示结果未知，先重新载入，不要反复提交。

## 旧文件与数据库升级

旧格式继续接受：

```json
{"standard_barcode": "001234-AbC"}
```

它作为**单条兼容导入**，用编号`LEGACY`替换整个清单，并应用到两个工位；不是在批量清单里追加一条。空字符串等价于清空。页面会提醒并确认这个行为。

已有v1工位数据库首次启动时先生成独立备份到`data/station-backups/`，然后事务性升级为schema v2。旧标准保持有效，解释为共享的LEGACY条目；旧结果不回填虚构的包装箱编号或名称。备份失败则停止升级；DDL失败回滚。旧`competition.sqlite3`仍不触碰。

更新前仍应停服并另行备份整个数据目录。旧版代码不能直接打开升级后的工位库；回退时停服，在新空数据目录使用升级前独立备份和旧版代码，不覆盖正在运行的WAL/SHM文件。真实标准文件放在仓库外或被忽略的`data/`中，不要提交到公开仓库。

## 接口

- `POST /api/admin/standard-barcode/import`：仍接收`content`（原始文件文本）、`revision`；支持批量和旧单条格式。仅此HTTP路径允许最多2 MiB的外层JSON正文，以容纳文件文本转义；解析后的UTF-8原文件仍限256 KiB。其余HTTP路径维持16 KiB限制，TCP帧上限不变。
- `POST /api/admin/standard-barcode/select`：`{"station":1,"box_id":"BOX01","revision":3}`。`box_id:null`取消该工位选择；只支持包装箱1/2工位，不接受工号作为选择依据。
- `/api/admin/state?project=packaging`新增`catalog`，含`boxes`、`selections`和`revision`；仅登录管理端可读。
- `GET /api/admin/standard-barcode/template?format=catalog`下载批量示例；不带参数仍返回旧单条示例。
- 旧`POST /api/admin/standard-barcode`保留，含义与单条兼容导入一致。

所有写入继续要求管理员登录、匹配的Origin、CSRF、X-Request-ID和当前revision。请求去重与标准历史保留；导入和结果入库共享写入锁与数据库事务，避免一个结果读到半份配置。

**TCP v2报文完全不变。** 参赛软件无须为本次批量标准功能调整上报格式。

测试记录见 [批量标准测试报告](TEST_REPORT_V1_4_CATALOG.md)。`SOURCE_MANIFEST.json`继续是v1.4.0发布快照，不代表后续Git增量提交。
