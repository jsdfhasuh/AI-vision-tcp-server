# 视觉比赛数据库使用说明（v1.2.0-db）

## 1. 这一版是什么

这是现有 TCP 裁判服务端和现场大屏的数据库增强版，不是另起一套数据源。沿用 SQLite，新增明确的结构版本、练习/正式场次区分、目标版本历史、数据库中的界面设置、分页历史查询、一致性备份和非覆盖恢复。服务端运行不需要安装第三方 pip 包或独立 MySQL 服务。

当前部署假设是一个裁判服务端进程管理一个本地数据库，参赛程序通过 TCP 上报，大屏通过 HTTP 读取脱敏快照。数据库文件不共享给参赛端、大屏电脑，也不开放远程 SQL 操作。

这不是完整赛事平台重写。相机截图上传、观众大字专属布局、评分规则版本化/改分审批、正式成绩发布及排行榜尚未实现。

## 2. 数据在哪里

双击 `start_server.cmd` 时默认使用解压目录下的：

```text
data/
  competition.sqlite3       主数据库
  competition.sqlite3-wal   运行时事务日志，可能存在
  competition.sqlite3-shm   运行时共享内存索引，可能存在
  competition.lock          防止重复运行的应用锁文件
  settings.json             旧版遗留文件，首次导入后不再作为设置来源
  backups/
    20260905_.../
      database.sqlite3      已完成的一致性备份，独立单文件
      manifest.json         备份原因、结构版本、计数、SHA256
```

直接执行 `python server.py` 与双击脚本的默认目录不同：前者延续旧版本，默认在用户本地应用数据目录 `VisionCompetitionTCP/data`。长期使用建议显式指定本地固定目录，避免换一个软件解压目录就看不到旧数据：

```powershell
.\start_server.cmd --data-dir "D:\VisionCompetitionData"
```

不要把活动数据库放在 SMB/NAS 网络共享、云盘实时同步目录或插拔式U盘上。其他电脑只访问服务端网页，不直接打开这份数据库。可将**完成后的备份文件夹**复制到U盘或其他介质。

SQLite 的 WAL 文件可能包含尚未合并到主文件的已提交事务。程序运行中不能只复制 `competition.sqlite3`，也不要手动删除 `-wal` 或 `-shm`。

## 3. 数据表

| 表 | 内容 |
|---|---|
| `sessions` | 场次编号、队伍、赛项、用途、客户端身份、创建/结束时间、状态、当前指定目标 |
| `rounds` | 测试轮次、样件类型、裁判预期、最终 OK/NG、核对结果、耗时、时限、目标快照、重传/重复/断线等计数 |
| `receipts` | 消息编号、指纹和确认回执，支持幂等重传，防止一个结果多次入账 |
| `audit` | 收发原始字节、连接事件、检测事件、恢复事件和设置保存事件 |
| `target_revisions` | 每个场次各个目标版本及快照，避免只保留最新箱型 |
| `settings` | 标题、副标题、端口、界面默认值等；不从旧 JSON 导入接入码等未知字段 |
| `schema_migrations` | 已应用的数据库结构版本和应用时间 |

`rounds` 关联场次；`receipts` 关联轮次；`target_revisions` 以场次+版本为联合主键。原始审计可能包含接入码、样件预期等私有信息。

新库结构版本为 2（`PRAGMA user_version`），具有应用标识 VCTC；这是**数据库结构版本**，不是客户端 TCP 协议版本。TCP 仍为 v1，每行 UTF-8 JSON，不需要让原客户端修改结果报文。

## 4. 正式与练习

主窗口新增“场次用途”：

- **练习联调 / PRACTICE**：默认用途。实际 TCP 调试也有完整记录，不冒充正式比赛。
- **正式比赛 / OFFICIAL**：创建前要求裁判确认，创建后用途锁定。
- **旧版未分类 / LEGACY**：从 v1.1 升级来的旧场次。由于旧版没有用途字段，程序不推断它们是正式还是练习。

不能在同一场次中途把练习改成正式。请新建正式场次，再重新测试。用途锁定同时有数据库触发器保护，但这不是防管理员篡改的安全系统。

大屏通过公共快照得到用途标签，只公开“正式比赛/练习联调”等标签，不公开裁判预期、样件类别、备注、核对正确性或接入码。练习和正式目前共用一份数据库，依靠明确字段及查询条件隔离，不是两个物理数据库。

## 5. 数据库管理窗口

启动后点击右上角“数据库管理”。这是裁判端窗口，**不要投屏此窗口**。

“查询”按队伍关键词（字面包含）、用途、赛项、UTC起止日期查询。每页50个场次，可翻页，不受主窗口历史下拉框最新500场的限制。日期留空不限；例如2026-09-05包含该UTC日，不是本地时区日历。

双击场次后，在主窗口只读查看记录。历史查看期间不能开始轮次、应用目标或取消当前轮；切回“当前场次”才能操作。主表仍只显示某场最近1000轮，导出包含该场全量已存记录。

“检查数据库”显示：结构版本、SQLite运行时版本、完整性检查、外键检查、各表计数、用途计数、主文件/WAL大小和剩余磁盘空间。它不会通过初始化 Store 的方式打开数据库，因此检查过程中不会把正在比赛的场次误标记为中断。

检查/备份/导出都在工作线程执行。裁判控制操作可能等待这些任务结束，但参赛结果仍由独立网络线程处理；不要把“后台任务”理解为具有硬实时磁盘性能保证。

## 6. 结果先提交，再确认

客户端发送结果后，服务端在一个事务中完成轮次结果更新、去重回执写入和 `RESULT_RECORDED` 审计事件写入，成功提交后才发送 ACK。写入失败会冻结比赛控制并断开客户端，不会假装已保存。

同消息编号同内容重传不会新增结果；同编号改内容或对已经保存的轮次提交另一份结果会被拒绝。已有最终结果的判定、核对值、接收时间、耗时和接收状态有触发器保护，允许累积重传等计数；界面不提供删除结果、直接修改最终结果或自动评分功能。

这些约束防止程序误操作，不是密码保护或防管理员篡改。数据库与备份均未加密，接入码也不是数据库加密密码。

## 7. 备份与恢复

### 手动备份

在数据库管理窗口点击“立即一致性备份”，选择上级目录。每次建立新文件夹，不覆盖旧备份。也可以运行：

```powershell
.\database_tools.cmd backup
.\database_tools.cmd --data-dir "D:\VisionCompetitionData" backup --output "D:\VisionCompetitionBackups"
```

程序使用 SQLite 在线备份 API，通过独立只读源连接复制已提交的一致数据库，再检查完整性，生成独立的 `database.sqlite3` 和 SHA256 清单。不是直接复制活动主文件。

每份备份是整个数据库的时间点快照，不是单个队伍的专属文件。场次切换后排队备份时，快照可能已经包含新场次的起始记录；清单中的审计最大编号用来辅助定位快照边界。

### 自动备份

升级 v1→v2 前、裁判界面切换关闭旧场次后、正常退出且存在场次时会触发备份。切换场次的备份由独立备份线程执行，待处理队列最多4项；未排入或失败会提示裁判补做，不能把排队视为已经备份成功。正常退出会等待已排队的备份结束。

程序异常退出不能保证执行“退出前备份”。已提交的主库事务和最近一次完成的备份才是恢复依据。自动备份不自动清理旧文件；定期检查磁盘空间，并将已经核验的备份转存到其他物理介质。与主库放在同一磁盘的备份不能应对该磁盘整体损坏。

### 恢复到新目录

恢复命令只接受本程序生成的完整备份目录。必须保留 `manifest.json` 和 `database.sqlite3` 两个文件。

```powershell
.\database_tools.cmd restore --backup "D:\VisionCompetitionBackups\20260905_..." --to "D:\VisionCompetitionRecovered"
.\start_server.cmd --data-dir "D:\VisionCompetitionRecovered"
```

目标必须是新目录或完全空目录。恢复时验证暂存副本SHA256、应用/结构版本、完整性和外键，再发布为目标数据库。不允许在线覆盖正在使用的主库，也不提供自动合并两份库。

恢复不会删除原数据。启动恢复库后，上次处于OPEN的场次和WAITING轮次标记为中断；已经提交的最终结果保留，旧轮次计时不恢复，新比赛应新建场次。

SHA256只能验证文件与清单是否一致；它不是独立可信的数字签名，不能防止同时修改文件和清单。

## 8. 从 v1.1 升级

1. 正常关闭旧服务端。备份重要证据；不要让旧程序与新程序同时操作同一数据目录。
2. 新版解压到独立软件目录，启动时用 `--data-dir` 指向**原来的数据目录**，不要误指到一个空的新目录。
3. 新版识别旧结构后先生成v1备份，再在事务中迁移。已有场次归为LEGACY，不猜测正式用途；旧版设置JSON首次导入数据库。
4. 打开数据库管理，核对队伍、轮次、最终结果、接收数量和目标快照，再运行模拟客户端联调。

旧目标版本只从旧库实际保留的轮次快照和当前目标中恢复，不能恢复从未保存过的中间版本。同一版本存在矛盾快照时迁移会拒绝自动合并，保留升级前备份供核查。

迁移中任一步失败会回滚结构修改；未知/未来版本拒绝打开，不强制降级。**不要再用 v1.1 程序打开已升级的数据库**：旧程序并不知道新版结构。需要回退时，使用升级前v1备份恢复到另一独立目录，再运行旧版。

## 9. 导出、计时和展板关联修正

导出使用独立只读事务取得一致快照，读取结束后再写CSV、JSON和计算哈希；整个文件写出阶段不再持有比赛引擎锁。汇总包含快照观测时间、审计最大编号和目标版本历史。仍可能受磁盘/CPU实际负载影响，正式时限请以现场验收为准。

客户端计时口径未变：服务端开始轮次到完整结果进入串行处理路径，不是纯推理耗时，也不是网卡收包时间。此次没有偷偷改成客户端自报计时。

大屏参考进度改用已接收结果数，取消轮次不会填满它；文案明确“非连续测试判定”（接收计数可能包含迟到结果）。这还不是独立的连续10轮验收批次。

未拿到相机阶段信息时只显示“待结果”；arm显示轮次已布置，trigger显示检测命令已下发，不再断言相机已经开始拍照。

## 10. SQLite 运行时与部署边界

数据库管理页显示的是当前Python实际绑定的SQLite版本，不只是Python版本。官方在2026年公布过WAL-reset修复：3.51.3及后续，另有3.44.6、3.50.7等回补。本工具会对不在已知修复范围的运行时提示检查，而不会把提示误报为已经发现数据库损坏。

本程序保持单个写连接，维护连接只读，不额外开启并发写入/检查点线程。但这不能替代升级到含官方修复的运行时，也不能作为断电、硬盘损坏或系统故障下绝不丢数据的承诺。禁止在比赛进行时用外部数据库工具执行写入或checkpoint。

一台裁判机、数台只读大屏的当前场景继续用SQLite。若将来多个裁判服务进程/多个赛场并发写同一中央数据库，再评估PostgreSQL等客户端/服务端数据库，并重新设计身份、权限与部署；不要直接共享当前SQLite文件冒充集中服务。
